# Rust: дополнительные проверки при ревью

Читать, когда ревью касается Rust, включая FFI, макросы и async.
Общие гейты, воспроизведение и формат отчёта — в [протоколе](../SKILL.md).
Примеры ниже — направления проверки, а не автоматические findings или исключения.

## Edition, toolchain и API

1. Открыть `Cargo.toml` проверяемого crate. Если edition наследуется через
   `edition.workspace = true`, открыть workspace manifest; записать эффективное
   значение и источник. Также проверить `rust-version`, toolchain и lint settings.
2. До замечания о синтаксисе сверить API с установленной версией зависимости и
   соответствующей документацией. Проверить пример компилятором этого проекта.
   Предупреждение и ошибка сборки — разные результаты; сохранить точный вывод.
3. При переходе между edition проверить применимые случаи:

| Случай | Что проверить в реальном crate/call site |
|---|---|
| `unsafe {}` внутри `unsafe fn` | Уровень `unsafe_op_in_unsafe_fn`, включая project `deny`/`forbid`; не объявлять lint ошибкой только по названию edition. |
| `unsafe extern "C" {}`, `#[unsafe(no_mangle)]`, `#[unsafe(export_name = "...")]` | Требования эффективной edition и поддержка toolchain; не называть принятый компилятором синтаксис лишним. |
| `-> impl Trait`, `+ use<'a, T>` | Какие параметры реально захватываются, ограничения lifetime и поведение существующих вызывающих. |
| `r#gen`, never-type fallback, временные значения `if let` и tail expression | Компилируемый пример с фактической edition; для времени уничтожения — наблюдаемый порядок `Drop`. |
| Итерация `Box<[T]>` | Конкретный вызов `.into_iter()`, его разрешение и тип элемента; не переносить результат другой edition. |

Например, сначала установить, откуда получено значение:

```toml
[package]
edition = "2024"
# либо edition.workspace = true — тогда читать workspace.package.edition
```

`#[expect(lint)]`, `LazyLock`/`LazyCell`, `async fn` в trait и
`#[diagnostic::on_unimplemented]` проверять относительно toolchain/MSRV;
наличие синтаксиса само по себе не доказывает возможность удалить зависимость.
Подробнее по Rust — [rust-code-review](../../rust-code-review/SKILL.md).

## Использования, traits и макросы

- Перед «unused» проверить публичный экспорт в другие crates, `#[cfg]`, тесты,
  обязательные методы trait, derive и использования через `From`/`Into`.
- Для **всех** реализаций trait выполнить оба запроса: generic и non-generic
  формы образуют разные множества. Прочитать найденные блоки и cfg:

```bash
ast-grep run -l rust --no-ignore hidden --no-ignore parent -p 'impl $T for $S { $$$ }'
ast-grep run -l rust --no-ignore hidden --no-ignore parent -p 'impl<$G> $T for $S { $$$ }'
```

- Текстовый поиск не раскрывает макросы. Проверить определение и настоящий вызов;
  для ошибки развёртки — минимальный компилируемый пример на этом toolchain.
- Для hygiene проверить, какие имена разрешаются в месте вызова и определения,
  экспортируется ли макрос, нужен ли `$crate`, поддерживается ли `no_std`.
  Внутренний макрос не освобождает от проверки конфликта имён на реальных вызовах.
- Для предложения заменить `:tt` на `:expr`/другой fragment проверить разбор
  существующих вызовов, неоднозначность и TT-munching сценарий.
- Перед замечанием о цене proc macro проверить `proc-macro = true`, включённые
  features (`syn` и т. п.) и измерить время компиляции затронутого сценария.

## Ошибки, владение и производительность

- Проследить `?` до вызывающего и верхнего обработчика; проверить error type,
  контекст и последствия потери сообщения. `let _ = tx.send(...)` оценивать по
  контракту доставки: закрытый receiver может быть ожидаемым или означать потерю.
- Для `unwrap()`/`expect()` найти достижимый вход, нарушающий предпосылку.
  Тестовое ожидание и production panic не равнозначны; проверка перед вызовом
  может доказывать инвариант. Отсутствие комментария — не воспроизведение panic.
- Для `.clone()` показать место в hot path и измеримый расход; проверить,
  проходит ли вариант с borrow компилятор и выполняет ли `Send`/`'static` контракт.
  `Arc::clone`, перенос в task и копирование в setup не являются дефектом сами по себе.
- Для allocation, formatting, `.collect()` и iterator/inlining предложений
  измерить реальную нагрузку. Startup/error path тоже может быть горячим;
  решение даёт измерение, а не название ветви.
- `Box<dyn Error>` в бинарнике, owned `String`, несколько `impl`, type aliases,
  `use super::*` в тестах, обоснованные lint attributes и длинный integration test
  не дают finding без нарушенного контракта. Placeholder не становится допустимым
  в результате ревью: действуют ограничения проекта.

## Unsafe и FFI

1. Для unsafe проверить фактический инвариант и его обеспечение вызывающими.
   SAFETY-комментарий не доказывает корректность; его отсутствие само по себе
   не воспроизводит memory-safety дефект. Наличие безопасного аналога — отдельная
   рекомендация, а не обязательное условие для сообщения об unsafe-дефекте.
2. Для layout сначала найти тип, который действительно пересекает границу ABI.
   Проверить `repr(C)`/`repr(transparent)`, вложенные поля, сигнатуру C и преобразования
   wrapper. Внутренний Rust-тип и opaque pointer не требуют одинакового вывода;
   отсутствие доступа к layout не снимает требования к lifetime и ownership.
3. Проследить передачу и возврат владения: `Box::into_raw`/`Box::from_raw`, allocator,
   число освобождений, null и повторное использование. Наличие пары в тексте
   не доказывает, что каждый достижимый путь освобождает значение ровно один раз.
4. Для `CString`/`CStr::as_ptr()` установить, как долго C хранит указатель.
   Одна lexical scope недостаточна, если C сохраняет pointer после возврата.
5. Для callback пройти достижимые panic paths и границу unwind, включая вызовы
   библиотек. Не считать «работает только с данными» доказательством отсутствия panic.
   Проверить применимость предлагаемого `catch_unwind` к текущей конфигурации.
6. Генерированный bindgen-код проверять вместе с декларациями/настройками генерации;
   количество `unsafe` не является дефектом. Сбой воспроизводить на ABI и платформе,
   где он заявлен; недоступную платформу явно записать в `unverified`.

## Concurrency и async

- Установить разделяемое состояние, операции и допустимый порядок событий.
  `Arc<Mutex<T>>`, канал или atomic не доказывают правильность составного протокола:
  воспроизвести нарушающий его порядок/seed, проверить блокировки и shutdown.
- Для memory ordering определить, публикуются ли вместе с atomic другие данные,
  и какое отношение happens-before требуется. Отдельный счётчик и публикация
  объекта различаются. Polling-loop сам по себе не доказывает синхронизацию или
  гарантированную видимость; более сильный ordering тоже требует обоснования.
- Для lock across await и блокирующей работы проверить scope guard и путь запуска,
  показать зависание/задержку соответствующей нагрузкой. Для короткой синхронной
  секции `std::sync::Mutex` не является автоматическим finding.
- Для task без join проверить владельца, shutdown и обработку ошибок; для
  `select!` — конкретный macro/API, ветви, cancellation и достижимость busy loop.
  Не переносить синтаксис одного macro в другой по сходству названий.
- `#[tokio::test]` с одним потоком, `#[should_panic]` и игнорирование ошибки cleanup
  оценивать по проверяемому контракту. Они не подтверждают поведение другой
  runtime-конфигурации. Подробнее — [tokio-async-code-review](../../tokio-async-code-review/SKILL.md).
