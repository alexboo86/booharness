## Wizard dependencies and apply phase

What stays live is `orchDependencies` of `ops/bootstrap/orch-dependencies.mjs`, the one dependency step the installer (`ops/bootstrap/install-harness.mjs`) runs: the marker `ops/orchestrator/node_modules/@modelcontextprotocol/sdk/package.json`, the npm resolution and the one `npm ci --omit=dev --ignore-scripts` argv. It covers three dependency sets (`DEPENDENCY_SETS`, `shippedSets`): the root (markers `yaml` and `typescript`; without it each orch command fails in `ops/bootstrap/skill-router.mjs` and the doctor's hook check fails), `ops/orchestrator`, and `ops/pi-runtime` (no Pi seat starts without it). The root and pi-runtime sets are tried only when their `package-lock.json` exists; the orchestrator set always. The installer installs each absent set and reports them under `dependencySets` (key absent when each set is present). A failed root or orchestrator set skips the service install; a failed pi-runtime set does not (the daemon and native seats do not need it). The argv gets `realpathSync` of the set directory after `--prefix`: npm 11.19.0 ends with `EUSAGE` when the prefix path crosses a symbolic link, as `/tmp` does on macOS. In a donor clone `--omit=dev` leaves `typescript` out and the step reports the root set missing after a zero exit.

The read-only LAN board port is asked of the installing agent too (`ops/harness-kit/INSTALL-PROMPT.md` (not in this kit)) with `get`, `set` and `unset`: `get` exits 1 for an absent key and that is an answer, not a failure. Default is the stored `orch.lanPort`; with no stored key the daemon default is port 7761. It stores `off` or an integer, never a digit string; the step never clears a stored key (`harness-config unset orch.lanPort` does).

The local memory installer is `ops/memory-local/install.mjs` when the tree holds that file (a built kit) and `install-memory.mjs` in the donor tree: the tree decides, nothing is copied. The kit installer (`ops/memory-local/install.mjs`) passes each `--forward` on to `install-memory.mjs`, for an install and for `--check` (a requested forward that is absent fails the check; a malformed value exits 2, as in the donor), and reloads the launchd unit only when a file changed or the unit is not loaded; it writes the unit file of a forward and no step loads it, as in the donor. `ops/harness-kit/test-memory-local.mjs` (not in this kit) pins this on macOS.

After a fresh `pi-runtime` install, `installOrchestrator` calls `refreshPiModels` (`ops/bootstrap/orch-dependencies.mjs`) to run the pinned `pi update --models` with a 60-second timeout and `PI_CODING_AGENT_DIR=<target home>/.pi/agent`. A cross-platform install reports `skipped` with a reason and runs no refresh. A same-platform refresh reports `refreshed` only when `models-store.json` lists every model of the imported `MODELS_OUTSIDE_PINNED_CATALOG`; else `incomplete` with missing models. No outcome skips the service install; a present dependency set makes no refresh call. A provider without a login gets no catalog even on exit 0; kimi seats require Pi's `kimi-coding` OAuth login; RPC seats read the saved store rather than refreshing. Proof: `scripts/test-orch-install.mjs` (not in this kit).
