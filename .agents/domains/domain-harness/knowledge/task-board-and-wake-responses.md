## Task board and wake responses

- The tasks board (contract `ops/orchestrator/TASKS-BOARD.md`) is `GET /tasks` on the loopback server only. `createTasksRoutes` (`ops/orchestrator/src/tasks-routes.ts`) wires `tasks-read.ts`, `tasks-write.ts`, `tasks-assign.ts`, `tasks-agent.ts` and serves `TASKS_PAGE`. The daemon only proxies: memoryd is the one writer; the board never closes a task itself and never deletes a row (delete = cancel with reason). Writes need the daemon's exact Origin and `X-Orch-Tasks: 1`.
- Read: every task not closed plus those closed within the window. A memoryd whose `applied` lacks `closed_since`/`fields` is never asked for a status-less list — the client fetches the four non-closed statuses, sets `memory.error`, keeps the answer until restart. A refusal passes through with status and message.
- Assign claims the task for a handle with a live chat binding and posts to that lead with wake (`{claimed:true, notified:false}` shows as failure). The notice tells the lead to start the task now, next or in parallel when busy, and to write its first step into the task. `/api/tasks/one` carries `notice` (`assignNotice`, `ops/orchestrator/src/tasks-notice.ts`: newest operator post with prefix `assignNoticePrefix(id)`, state from `chatList` via the optional `post` selector), re-read every 5 s until `read`.
- Advice and duplicate search run one scout seat each, found by title (`Task advice #<id>`), so the store gets no new table. The drawer renders the advice report as text (`renderAdvice`, `ops/orchestrator/src/tasks-page-actions.ts`): `forLead`, claims with evidence, the not-checked list, folded checked/unknown keys. The board speaks the bare domain name (`harness`), the store the routing id (`domain-harness`).
- The page uses no `window.prompt`/`confirm`/`alert` (the Claude app browser pane throws on `prompt()`): reasons/evidence go through an inline `.confirm` form (`askText`). The batch bar (`tasks-page-batch.ts`, mounted third) replays the single routes over the selection; the selection keeps only on-screen rows (`dropFolded`/`render` in `tasks-page.ts`). Drag and drop (`tasks-page-dnd.ts`, mounted fourth; task 2985): cards sit in four status columns (Open, In progress, Blocked, Done); a column drop runs the card drawer's action with its confirmation, a drop on its own column does nothing. Domain chips post `/api/tasks/update {id, domain}` per carried id whose domain differs; a selected source carries the selection for domain drops only. Headers link `/` and `/tasks`.
- Wake: with `wake: true` the `chat_post` answer adds `addressees`, one row `{handle, state, lastSeen, desktop}` per live addressee except the author (`chatAddressees`, `ops/orchestrator/src/chat.ts`); without wake it answers `{id, at}`. `state`: `watcher` (a `/chat/wake` poll held for the session), `in turn` (session's last `/chat/unread` or `/chat/wake` under 3 minutes old; in-memory map in `ops/orchestrator/src/http.ts`, empty after restart), else `no watcher`. `lastSeen` = latest of that request, latest receipt, `bound_at`. `desktop` = desktop session id stored by `chat_join {handle, session, desktop?}` in `chat_bindings.desktop` (store schema 8, `ops/orchestrator/src/store.ts`; ≤80 characters, no whitespace; a same-binding join updates only that column; no `desktop` keeps the stored value; SessionStart names it via `get_session "self"`, `ops/bootstrap/session-start.mjs`). The answer never carries a post body. Older daemon code refuses a schema 8 store: a revert needs the store backup or a forward fix.
