## Wait, daemon state, and schema repair

- `orch wait` takes one turn id or several. One: `waitOne` (`ops/orchestrator/src/main.ts`) keeps bytes and exit code. Several: `waitMany` long-polls all ids; after the first end it collects for the grace (`BATCH_GRACE_SECONDS`, 180 s, `--grace-seconds`), never past the deadline; prints ended digests in argument order + `still running: <ids>; wait again: <command>`; `--json` prints `{turns, running}`. Exit 0 all done, 1 one ended otherwise or orch unreachable, 3 timeout with nothing ended. A read-only seat's guard accepts one id only (`ops/orchestrator/src/seat-guard.ts`).
- Output is the text digest (`ops/orchestrator/src/digest-text.ts`); a live daemon pid whose health times out is busy and retried, a refused port is stale (`ops/orchestrator/src/lock.ts`). `status`, `restart` (`--when-idle`, `--cancel`), `lesson-repeat` and Windows `stop` resolve the daemon via `runningInstance`: a live pid that does not answer health is `running: true` + `healthUnanswered: true` (status exits 0; other verbs refuse as busy without signalling); a dead pid, refused port or foreign health answer is not running.
- Lock (`acquireLock`/`holderOf`, `ops/orchestrator/src/lock.ts`) asks neither port nor health: the record holds `born`, the pid's OS start time; an equal start time holds the lock, a different one is a reused stale pid, a missing `born` or unanswered start time is refused as held (fail closed). A daemon with no lock holder or a refused connection is ridden out up to `DOWN_GRACE_MS` (5 min) of continuous outage; an answer resets the clock; past it wait reports `orch is not running` (`ops/orchestrator/src/main.ts`).
- Boards: loopback `http://127.0.0.1:7760/` + `GET /api/dashboard`; a second read-only listener on all interfaces serves only `GET /`, `GET /api/dashboard`, `GET /api/chat` and 404s the rest (`createLanBoardServer`, `ops/orchestrator/src/http.ts`). Port: `ORCH_LAN_PORT` (default 7761; `off`/0 starts none); Mac config `orch.lanPort` (`"off"` or integer 1–65535, never a numeric string — `lanPortRefusal`, `scripts/lib/harness-config.mjs`), written into the launchd plist by `renderPlist` (`ops/orchestrator/install.mjs`) only when present (public kit ships `off`, `ops/harness-kit/build-kit.mjs` (not in this kit)); the Windows task passes `serve --lan-port <off|port>` (`renderTaskXml`), which outranks the variable (same parser `parseLanPort`). The LAN chat feed is read-only: posts + per live handle only `handle` and `bound_at` (never session id, never desktop id), `watchers`, `readOnly: true` (board hides post/release forms); write routes, `/tasks`, `/mcp` and non-GET stay 404 (no token); the page carries no load or active session identities.

- Schema repair never loses the refused report: the first refusal is pinned, quoted between non-backtick delimiters, capped at 16000 characters (`repairPrompt`, `ops/orchestrator/src/report.ts`). `accountRepair` compares the first fenced block of original and repair: fewer findings than min(original, `MAX_FINDINGS`) or a missing `changedFiles` entry → rejected, the turn keeps the original text unparsed (`seat_report` returns it whole), digest flag `schema repair rejected`; reworded findings, removed keys and a cut to `MAX_FINDINGS` pass. Flags ride the turn's grade JSON (`reportRepairFlags`, `reportRepairRejected`).
- A turn that continues after a report keeps the earlier report when the last reply loses it: the Pi adapter returns earlier assistant texts as `earlier` (`ops/orchestrator/src/providers/pi.ts`); before the repair loop `seats.ts` takes the last earlier text that parses; if the last reply does not parse or `accountRepair` names a loss, that earlier text becomes the turn text with a `continuation reply rejected` digest flag (the dropped reply's check outcome survives). A complete later update is accepted unchanged; a full final report with prose around its fence yields to the earlier report and gets no repair round.
